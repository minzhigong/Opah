## 1. 产品概述

### 1.1 一句话定位

Opah 是一款通过 Web UI 完成运维工作的一站式工具：从 Git 仓库拉取代码，自动构建 Docker 镜像，实现一键式部署与持续运维。

### 1.2 背景与问题

中小团队和独立开发者当前的部署运维流程普遍存在以下痛点：

- **流程割裂**：拉代码、构建镜像、上传镜像、登服务器重启服务，分散在本地终端、CI 平台、服务器 SSH 之间，需要多人或多工具协作。
- **门槛偏高**：要求使用者熟悉 Git、Docker、Shell、Nginx、 systemd 等一整套工具链。
- **重复劳动**：每次发版重复执行相同的构建与部署命令，容易漏步骤、出错。
- **缺乏可视化管理**：服务器上跑了哪些服务、什么版本、占用多少资源，没有一个统一的地方查看。

### 1.3 产品愿景

让"从代码到上线"变成一次点击：开发者提交代码后，在浏览器里即可完成构建、部署、回滚、监控等全部运维工作。

### 1.4 目标用户

| 用户群体 | 典型场景 |
| --- | --- |
| 独立开发者 / 个人项目 | 个人项目频繁发版，不想手动 SSH 操作 |
| 小型创业团队（无专职运维） | 开发者兼任运维，希望降低运维心智负担 |
| 中小企业运维人员 | 管理多台服务器上的多个服务，需要统一入口 |
| 内部平台团队 | 为公司内部提供私有化的部署平台 |

---

## 2. 核心价值主张

1. **一站式**：Git 拉取 → Docker 构建 → 部署 → 运维监控，全流程在同一个 Web UI 内完成。
2. **一键式**：常用操作（部署、重启、回滚）一次点击完成，底层命令自动编排。
3. **低门槛**：不需要记忆命令，通过界面引导完成原本需要终端操作的运维任务。
4. **可回滚**：每次部署保留镜像版本记录，出问题可快速回退到历史版本。

## 3. 功能需求

### 3.1 功能架构总览

```
Opah
├── 项目管理（Git 集成）
├── 构建管理（Docker 镜像构建）
├── 部署管理（一键部署 / 回滚）
├── 主机管理（服务器接入）
├── 运维监控（状态 / 日志 / 资源）
└── 系统管理（用户 / 权限 / 审计）
```

### 3.2 模块详细说明

#### 3.2.1 项目管理

| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| PROJ-01 | 关联 Git 仓库 | 支持输入仓库地址接入项目（HTTPS / SSH），兼容 GitHub / GitLab / Gitee / 自建仓库 | P0 |
| PROJ-02 | 凭据管理 | 管理访问私有仓库所需的账号 / Token / SSH Key | P0 |
| PROJ-03 | 分支与提交选择 | 部署时可选择分支、Tag 或指定 commit | P0 |
| PROJ-04 | 项目列表 | 展示项目名、最近部署时间、当前运行版本、运行状态 | P0 |
| PROJ-05 | 自动检测变更 | 可配置轮询或 Webhook 触发，检测到新提交后提示可部署 | P1 |

#### 3.2.2 构建管理

| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| BUILD-01 | 自动识别构建配置 | 读取项目内 `Dockerfile`；无 Dockerfile 时可根据语言（Node / Java / Python / Go）使用内置模板生成 | P0 |
| BUILD-02 | 镜像构建 | 拉取代码后在构建环境中执行 `docker build`，产出带版本标签的镜像 | P0 |
| BUILD-03 | 构建日志实时查看 | Web UI 实时滚动展示构建输出，失败时高亮错误行 | P0 |
| BUILD-04 | 镜像版本管理 | 每次构建生成唯一版本号（如时间戳 + commit 短 hash），历史镜像可查询 | P0 |
| BUILD-05 | 构建历史 | 记录每次构建的状态、耗时、触发人、commit 信息 | P1 |
| BUILD-06 | 构建缓存 | 利用 Docker layer cache 加速重复构建 | P1 |

#### 3.2.3 部署管理

| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| DEPLOY-01 | 一键部署 | 选择项目版本 + 目标主机，点击即可完成部署，自动处理旧实例停止与新实例启动 | P0 |
| DEPLOY-02 | 单机部署 | 将镜像分发到单台主机并以容器形式运行 | P0 |
| DEPLOY-03 | 环境变量与端口配置 | 部署时可配置环境变量、端口映射、挂载目录、重启策略 | P0 |
| DEPLOY-04 | 一键回滚 | 从历史版本列表中选择任一版本，一键回退 | P0 |
| DEPLOY-05 | 多主机部署 | 同一服务部署到多台主机，支持滚动更新（先起后停，减少停机时间） | P1 |
| DEPLOY-06 | 定时部署 | 支持预约在指定时间执行部署 | P2 |
| DEPLOY-07 | Compose 编排部署 | 支持含 `docker-compose.yml` 的多容器项目（如应用 + 数据库）作为整体部署、启停与回滚 | P0 |

| HOST-02 | 主机列表 | 展示主机在线状态、IP、系统信息、CPU / 内存 / 磁盘使用率 | P0 |
| HOST-03 | 容器概览 | 查看指定主机上运行的全部容器及其状态 | P0 |

## 4. 典型使用流程

### 4.1 首次接入项目（5 分钟上线）

1. 在 Web UI 填写 Git 仓库地址与访问凭据；
2. 选择分支，Opah 拉取代码并识别/生成构建配置；
3. 选择目标主机，配置端口与环境变量；
4. 点击「部署」——Opah 自动完成：拉取代码 → 构建镜像 → 分发到主机 → 启动容器；
5. 部署完成后在 Dashboard 看到服务运行状态与访问地址。

### 4.2 日常发版

1. 本地提交代码并 push；
2. Opah 检测到新提交（Webhook 或手动刷新）；
3. 点击「部署最新版本」，等待构建与发布完成；
4. 验证异常时点击「回滚」，10 秒内恢复上一版本。

### 4.3 日常运维

- 打开 Dashboard 查看全部服务健康状态；
- 服务异常时查看实时日志定位问题，必要时一键重启或进入 Web 终端排查。

## 5. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 安全 | 凭据（SSH Key / Token）加密存储；Web 会话鉴权；所有操作走最小权限原则 |
| 性能 | 构建日志推送延迟 < 1s；常用页面首屏加载 < 2s |
| 可靠性 | Opah 自身异常重启不影响的已运行容器；部署中途失败不破坏旧版本（先保留旧实例） |
| 兼容性 | 主流浏览器（Chrome / Edge / Firefox）；主机端支持 Linux（Docker 20+） |
| 部署形态 | 双平台：Windows 本机运行（主用，直连 Docker Desktop）或 Linux Docker Compose |

## 6. 版本规划

### MVP（v0.1）—— 验证核心闭环

- 项目管理：PROJ-01 / 02 / 03 / 04
- 构建管理：BUILD-01 / 02 / 03 / 04
- 部署管理：DEPLOY-01 / 02 / 03 / 04 / 07（单机部署，含 Compose 多容器项目）
- 主机管理：HOST-01 / 02 / 03
- 运维监控：OPS-01 / 02 / 03
- 系统管理：SYS-01（单管理员）

**MVP 验收标准：** 一个含 Dockerfile 的 Git 项目，从接入到单机运行，全程仅通过 Web UI 操作完成，且可一键回滚。

### v0.2 —— 团队可用

- Webhook 自动触发、构建缓存
- 多主机部署与滚动更新
- 告警通知（邮件 / Webhook）
- 操作审计、多用户基础支持

### v1.0 —— 平台化

- 多角色权限体系、对外 API
- Web 终端、资源监控图表
- 定时部署、部署工作流编排（如构建后自动执行健康检查）

## 7. 竞品参考与差异化

| 产品 | 特点 | Opah 差异化 |
| --- | --- | --- |
| Portainer | 专注 Docker/K8s 容器管理，不含 CI 构建 | Opah 覆盖"代码 → 镜像 → 部署"全链路 |
| Dokploy / Coolify | 面向 PaaS 场景的部署平台 | Opah 更聚焦传统服务器上的项目部署运维，保持轻量 |

## 8. 风险与待确认问题

| 编号  | 问题                  | 说明                                 | 回答                                              |
| --- | ------------------- | ---------------------------------- | ----------------------------------------------- |
| Q1  | 技术栈选型               | 后端、前端框架、构建执行方式（见 8.1）              | **已定**：后端 Java，前端 React；构建执行方式挂载宿主机 docker.sock |
| Q2  | 镜像分发方式              | 远程构建 vs 中心构建 + 镜像仓库（对比见 8.2）       | **已定**：中心构建 + save/load 经 SSH 分发（方案③，v0.2 修订，原定方案②） |
| Q3  | 是否支持 Docker Compose | 多容器项目（如应用 + 数据库）是否纳入 MVP 范围        | **已定**：是（DEPLOY-07 已纳入 MVP）                     |
| Q4  | 是否考虑 K8s            | 初期明确不支持 K8s、聚焦 Docker 单机/多机，还是预留扩展 | **已定**：不支持 K8s，聚焦 Docker 单机/多机，面向小型项目           |
| Q5  | 商业形态                | 开源 / 开源+付费托管 / 纯商业产品，影响后续功能取舍      | **已定**：开源免费                                     |

### 8.1 构建执行方式说明（Q1）

指 `docker build` 在哪里执行，两个候选：

| 方式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 复用宿主机 Docker（推荐） | Opah 容器挂载 `/var/run/docker.sock`，直接调用宿主机 Docker daemon 构建 | 实现简单；可利用宿主机 layer 缓存加速构建 | Opah 拥有宿主机 Docker 完全控制权（等同 root 权限）；多构建任务间不隔离 |
| B. 独立构建容器（DinD） | 每次构建在隔离的一次性容器中运行独立的 Docker daemon | 安全隔离性好 | 需处理嵌套 Docker 的缓存与存储，复杂度高 |

同类开源产品（Portainer、Dokploy）均采用方式 A。**MVP 采用方式 A**，未来如做多租户 SaaS 再演进到方式 B。

### 8.2 镜像分发方式对比（Q2，已定：方案③）

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| ① 远程构建 | SSH 到每台目标主机执行 git pull + docker build | 架构最简单；无需传输镜像；构建缓存就在本机 | N 台主机构建 N 次；目标主机需保存 Git 凭据（扩大攻击面）；构建占用业务机资源；各主机产物可能有差异 |
| ② 中心构建 + 内置 Registry | Opah 中心构建一次 → 推送至自带 registry 容器 → 各主机 `docker pull` | 一次构建处处运行；主机无需 Git 凭据；历史镜像均在 registry，回滚秒级；多主机扩展自然 | 需维护镜像存储（磁盘占用）；多一个组件；目标主机需配置 insecure-registries |
| ③ 中心构建 + save/load 传输 | 中心构建后 `docker save` 流式导出，经 SSH 管道到目标主机 `docker load` | 无需 registry 与任何主机侧配置；实现最简单；构建机可控外网（代理拉基础镜像） | 全量 tar 传输、无分层缓存，大镜像慢；多主机需逐台分发 |

**v0.2 修订为方案③**，原因：

- 国内服务器拉取境外镜像（Docker Hub 及多数公共加速源的回源 CDN）常被阻断，而构建侧可用可控外网的 Windows 本机，基础镜像拉取不受限；
- server 调整为双平台运行（Windows 裸跑为主用形态），方案②的 registry 容器与目标主机 insecure-registries 配置成为纯负担；
- 方案③缺点的缓解：回滚优先复用目标主机本地已 load 的历史镜像，零传输秒级；多主机分发可并发执行；`docker save | ssh docker load` 流式管道不落地完整 tar，无双倍磁盘峰值。

## 9. 术语表

| 术语 | 定义 |
| --- | --- |
| 项目（Project） | 接入 Opah 的一个 Git 仓库对应的可部署单元 |
| 版本（Version） | 一次构建产出的镜像，由时间戳 + commit 标识 |
| 主机（Host） | 通过 SSH 接入 Opah、运行 Docker 的目标服务器 |
| 部署（Deploy） | 将指定版本镜像在指定主机上以容器形式运行的过程 |
| 回滚（Rollback） | 将服务回退到某个历史版本运行 |
