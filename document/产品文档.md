## 1. 产品概述

### 1.1 一句话定位

Opah 是一款面向个人开发者与小团队的一站式运维部署工具：运行在用户自己的 Windows/Linux 机器上，自动拉取 Git 代码、构建 Docker 镜像，并把服务以容器形式一键部署到远程 Linux 服务器，全程在 Web UI 完成，无需手工 SSH 操作。

### 1.2 背景与问题

中小团队和独立开发者当前的部署运维流程普遍存在以下痛点：

- **流程割裂**：拉代码、构建镜像、上传镜像、登服务器重启服务，分散在本地终端、CI 平台、服务器 SSH 之间，需要多个工具来回切换。
- **门槛偏高**：要求使用者熟悉 Git、Docker、Shell、Nginx、systemd 等一整套工具链。
- **重复劳动**：每次发版重复执行相同的构建与部署命令，容易漏步骤、出错。
- **缺乏统一视图**：服务器上跑了哪些服务、什么版本、占用多少资源，没有一个统一的地方查看。
- **网络环境受限**：国内服务器拉取境外基础镜像常被阻断，直接在服务器上构建不可行。

### 1.3 产品愿景

让"从代码到上线"变成一次点击：开发者提交代码后，在浏览器里即可完成构建、部署、回滚、监控等全部运维工作。

### 1.4 目标用户

| 用户群体 | 典型场景 |
| --- | --- |
| 独立开发者 / 个人项目 | 个人项目频繁发版，不想手动 SSH 操作 |
| 小型创业团队（无专职运维） | 开发者兼任运维，希望降低运维心智负担 |
| 中小企业运维人员 | 管理多台 Linux 服务器上的多个服务，需要统一入口 |
| 内部平台团队 | 为公司内部提供私有化的部署平台 |

### 1.5 设计原则

1. **安装即用**：Opah 本身提供一键式安装；Windows 上提供一键式启动方案，不要求用户理解 Docker、Compose 等底层概念。
2. **一期聚焦**：管理的服务一期聚焦 Java 后端与 React、Vue 前端项目，把体验做好，后续再扩展语言与框架。
3. **轻量优先**：不引入 K8s、不内置 Registry 等重组件，面向单机/少量服务器的传统部署场景。
4. **开源免费**：以开源免费形态发布，不设商业付费门槛。

## 2. 核心价值主张

1. **一站式**：Git 拉取 → Docker 构建 → 分发部署 → 运维监控，全流程在同一个 Web UI 内完成。
2. **一键式**：安装 Opah 一键、启动 Opah 一键、部署/重启/回滚也各只需一次点击，底层命令自动编排。
3. **低门槛**：不需要记忆命令，通过界面引导完成原本需要终端操作的运维任务。
4. **可回滚**：每次部署保留镜像版本记录，出问题可快速回退到历史版本。
5. **友好应对受限网络**：构建在用户本机执行（可走代理拉取基础镜像），服务器侧零外网依赖、零额外配置。

## 3. 产品形态与运行架构

### 3.1 两种角色

| 角色 | 说明 |
| --- | --- |
| Opah 运行端（管理端） | 用户自己的电脑或服务器。双平台支持：**Windows 本机裸跑（一期主用形态）**，或 Linux 上以 Docker Compose 运行 |
| 目标主机（被管理端） | 运行业务服务的 Linux 服务器，通过 SSH 接入 Opah，服务一律以 Docker 容器形式部署与管理 |

### 3.2 核心链路

```
Git 仓库 ──拉取──> Opah（用户本机）
                    │ docker build（本机 Docker，可走代理拉基础镜像）
                    ▼
                 版本化镜像
                    │ docker save 流式导出 + SSH 管道 docker load
                    ▼
              Linux 目标主机 ──启动/更新──> 业务容器（Java 服务 / React·Vue 前端）
```

- 构建在 Opah 运行端本机执行（复用宿主 Docker daemon，非 DinD）；
- 镜像分发采用 `docker save | ssh docker load` 流式管道，不落地完整 tar，无 Registry 组件，目标主机零配置。

### 3.3 安装与启动体验（一期重点）

| 环节 | 目标 |
| --- | --- |
| 安装 | Windows 提供绿色自包含包（zip，内嵌裁剪 JRE），解压即完成安装，零手工配置、无需管理员权限 |
| 启动 | Windows 上一键启动：双击即拉起 Opah 服务并打开 Web UI；自动检测 Docker Desktop，未安装/未启动时给出引导 |
| 运行期 | Opah 异常退出不影响已部署在服务器上的业务容器 |
| 升级 | Opah 自身版本升级不破坏已有配置与已部署服务（一期可接受手工替换，交互引导做到位即可） |

## 4. 功能需求

### 4.1 功能架构总览

```
Opah
├── 安装与启动（一键安装 / 一键启动）
├── 主机管理（SSH 连接信息 / 服务器接入）
├── 项目管理（Git 集成）
├── 构建管理（Docker 镜像构建，一期 Java / React / Vue）
├── 部署管理（一键部署 / 回滚 / Compose 编排）
├── 配置管理（配置中心 / Nginx 配置）
├── 运维监控（状态 / 日志 / 资源）
└── 系统管理（用户 / 权限 / 审计）
```

### 4.2 模块详细说明

#### 4.2.1 安装与启动

| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| INST-01 | 绿色自包含包 | Windows 绿色版：zip 内含 exe 与内嵌裁剪 JRE，解压双击即用（Q7 已定）；v0.2 补充安装向导形态 | P0 |
| INST-02 | Windows 一键启动 | 双击启动 Opah 并自动打开 Web UI，无需命令行 | P0 |
| INST-03 | Docker 环境检测引导 | 启动时检测 Docker Desktop 是否可用，异常时给出修复引导 | P0 |
| INST-04 | Linux Compose 运行 | 提供 docker-compose.yml 与部署脚本，Linux 上一条命令拉起 | P1 |
| INST-05 | 平滑升级 | Opah 升级保留配置，不影响已部署服务 | P2 |

#### 4.2.2 主机管理

| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |

| HOST-02 | 主机接入检测 | 添加时自动测试连通性，检测 Docker 环境，缺失时引导安装 | P0 |
| HOST-03 | 主机列表 | 展示主机在线状态、IP、系统信息、CPU / 内存 / 磁盘使用率 | P0 |
| HOST-04 | 容器概览 | 查看指定主机上运行的全部容器及其状态 | P0 |
| HOST-05 | 健康检查 | 定期探活，主机离线时告警通知 | P1 |

#### 4.2.3 项目管理

| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| PROJ-01 | 关联 Git 仓库 | 支持输入仓库地址接入项目（HTTPS / SSH），兼容 GitHub / GitLab / Gitee / 自建仓库 | P0 |

## 5. 典型使用流程

### 5.1 安装与首次使用

1. 下载 Windows 绿色包（zip），解压即完成安装；
2. 双击启动，Opah 自动检测 Docker 环境并打开 Web UI；
3. 首次进入设置管理员账号；
4. 添加目标服务器：填写 SSH 连接信息，Opah 自动验证连通性与 Docker 环境。

### 5.2 首次接入项目（5 分钟上线）

1. 在 Web UI 填写 Git 仓库地址与访问凭据；
2. 选择分支，Opah 拉取代码并识别/生成构建配置（Java / React / Vue 模板）；
3. 选择目标主机，配置端口与环境变量；
4. 点击「部署」——Opah 自动完成：拉取代码 → 本机构建镜像 → save/load 分发到主机 → 启动容器；
5. 部署完成后在 Dashboard 看到服务运行状态与访问地址。

### 5.3 日常发版

1. 本地提交代码并 push；
2. Opah 检测到新提交（Webhook 或手动刷新）；
3. 点击「部署最新版本」，等待构建与发布完成；
4. 验证异常时点击「回滚」，秒级恢复上一版本。

### 5.4 日常运维

- 打开 Dashboard 查看全部服务健康状态；
- 服务异常时查看实时日志定位问题，必要时一键重启或进入 Web 终端排查。

## 6. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 安全 | SSH 凭据 / Git Token 加密存储；Web 会话鉴权；操作走最小权限原则 |
| 性能 | 构建日志推送延迟 < 1s；常用页面首屏加载 < 2s |
| 可靠性 | Opah 自身异常重启不影响已运行容器；部署中途失败不破坏旧版本（先保留旧实例） |
| 兼容性 | 主流浏览器（Chrome / Edge / Firefox）；目标主机支持 Linux（Docker 20+） |
| 部署形态 | 双平台：Windows 本机裸跑（主用，直连 Docker Desktop）或 Linux Docker Compose |
| 易用性 | Windows 安装到首次部署成功，全程不出现命令行操作（引导式排除 Docker 环境问题除外） |

## 7. 版本规划

### MVP（v0.1）—— 验证核心闭环

- 安装与启动：INST-01 / 02 / 03
- 主机管理：HOST-01 / 02 / 03 / 04
- 项目管理：PROJ-01 / 02 / 03 / 04 / 06
- 构建管理：BUILD-01 / 02 / 03 / 04（Java + React + Vue 模板）
- 部署管理：DEPLOY-01 / 02 / 03 / 04 / 07（单机部署，含 Compose 多容器项目）

**MVP 验收标准：** 在一台全新 Windows 电脑上安装 Opah，接入一个 Java 或前端（React / Vue）的 Git 项目（前后端同仓库时拆分为独立部署单元分别上线），从安装到服务运行在远程 Linux 主机上，全程仅通过 Web UI 完成，且可一键回滚。

### v0.2 —— 团队可用

- Webhook 自动触发、构建缓存
- 多主机部署与滚动更新
- 告警通知（邮件 / Webhook）
- 操作审计、多用户基础支持
- 配置版本化与回滚（CONF-03）
- Windows 安装向导形态（INST-01 扩展）
- Linux Compose 运行形态完善（INST-04）

### v1.0 —— 平台化

- 多角色权限体系、对外 API
- Web 终端、资源监控图表
- 定时部署、构建模板语言扩展（Python / Go 等）
- 部署工作流编排（如构建后自动执行健康检查）

## 8. 竞品参考与差异化

| 产品 | 特点 | Opah 差异化 |
| --- | --- | --- |
| Portainer | 专注 Docker/K8s 容器管理，不含 CI 构建 | Opah 覆盖"代码 → 镜像 → 部署"全链路 |
| Dokploy / Coolify | 面向 PaaS 场景的部署平台 | Opah 更聚焦传统服务器上的项目部署运维，保持轻量 |
| Jenkins + 脚本 | 功能强大但配置复杂、UI 陈旧 | Opah 零配置上手，面向不会用 CI 的用户 |

> 竞品定位需在技术调研阶段进一步确认，此表为初稿判断。

## 9. 关键决策记录

以下决策均已确认，后续架构与功能取舍遵循此表：

| 编号  | 问题                  | 决策                                                           | 主要原因                                                                                       | 回答        |
| --- | ------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | --------- |
| Q1  | 技术栈选型               | 后端 Java，前端 React；构建复用宿主机 Docker daemon（非 DinD）               | 与被管理的 Java/React 项目同栈，降低维护成本；DinD 复杂度高，同类产品均复用宿主 Docker                                    | 接受        |
| Q2  | 镜像分发方式              | 中心构建 + `docker save` 流式导出 + SSH 管道 `docker load`（无 Registry） | 国内服务器拉境外镜像被阻断，而 Windows 本机可走代理；无 Registry 则目标主机零配置。缓解：回滚优先复用目标主机本地镜像；多主机并发分发；流式管道不落地完整 tar | 接受        |
| Q3  | 是否支持 Docker Compose | 支持，多容器项目纳入 MVP（DEPLOY-07）                                    | Java + 数据库 + 前端是典型组合                                                                       | 接受        |
| Q4  | 是否支持 K8s            | 不支持，聚焦 Docker 单机/多机                                          | 面向小型项目，保持轻量                                                                                | 接受        |
| Q5  | 商业形态                | 开源免费                                                         | —                                                                                          | 接受        |
| Q6  | 一期语言范围              | 管理的服务一期聚焦 Java 后端与 React、Vue 前端，模板化支持，后续扩展                     | 见初期构想；先把核心链路体验做好                                                                           | 前端也要支持vue |
| Q8  | 配置与 Nginx 管理       | Opah 内置配置中心：集中管理部署项目的配置并随部署注入；前端 Nginx 支持在 UI 中配置（见 4.2.6 CONF 模块） | 部署配置不应散落各服务器手工维护；前端镜像需可参数化 | Opah提供配置中心能力，部署项目自带的配置，以及nginx要支持配置 |
| Q9  | 前后端组合项目            | 支持 monorepo：前后端可同仓库，但作为独立部署单元分别构建、部署与回滚（PROJ-06） | 前后端发版节奏不同，生命周期需独立 | 前后端可能在同一个仓库中，但是部署要分离 |

## 10. 术语表

| 术语 | 定义 |
| --- | --- |
| 项目（Project） | 接入 Opah 的一个 Git 仓库对应的可部署单元 |
| 版本（Version） | 一次构建产出的镜像，由时间戳 + commit 标识 |
| 主机（Host） | 通过 SSH 接入 Opah、运行 Docker 的 Linux 目标服务器 |
| 部署（Deploy） | 将指定版本镜像分发到指定主机并以容器形式运行的过程 |
| 回滚（Rollback） | 将服务回退到某个历史版本运行 |
| 分发（Distribute） | `docker save` 流式导出镜像并经 SSH 管道在目标主机 `docker load` 的过程 |
| 部署单元（Deployable Unit） | 仓库中可独立构建、部署、回滚的一个服务；一个 Git 仓库可包含多个部署单元（PROJ-06） |
| 配置中心（Config Center） | Opah 内置的配置管理能力，按项目/环境管理配置并在部署时注入容器 |
