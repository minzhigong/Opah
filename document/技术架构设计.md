## 1. 架构总览

### 1.1 部署视角

Opah 以 docker-compose 方式交付，包含两个容器：

```
┌────────────────────────── Opah 宿主机 ──────────────────────────┐
│                                                                  │
│  ┌──────────────────┐        ┌──────────────────┐               │
│  │  opah-server     │        │  opah-registry   │               │
│  │  (Spring Boot)   │───────▶│  (registry:2)    │               │
│  │  - REST API      │ push/  │  内置镜像仓库     │               │
│  │  - WebSocket     │ pull   └────────┬─────────┘               │
│  │  - 内嵌数据库     │                 │ volume                  │
│  └───┬──────┬───────┘        ┌────────▼─────────┐               │
│      │      │                │  /var/lib/registry│               │
│  docker.sock│                └──────────────────┘               │
│      │      │                                                   │
│  ┌───▼──────▼───────┐        ┌──────────────────┐               │
│  │  宿主机 Docker    │        │  /data/opah      │               │
│  │  daemon (构建)    │        │  SQLite + 配置    │               │
│  └──────────────────┘        └──────────────────┘               │
└──────────────┬───────────────────────────────────────────────────┘
               │ SSH（无 Agent，直接执行 docker 命令）
   ┌───────────┼─────────────┐
   ▼           ▼             ▼
┌───────┐  ┌───────┐    ┌───────┐
│主机 A  │  │主机 B  │    │主机 C  │   目标主机：仅需 SSH + Docker
│docker │  │docker │    │docker │
└───────┘  └───────┘    └───────┘
```

### 1.2 逻辑分层

```
┌─────────────────────────────────────────────┐
│  前端 opah-web（React SPA）                   │
├─────────────────────────────────────────────┤
│  接入层   REST Controller / WebSocket 端点    │
├─────────────────────────────────────────────┤
│  应用层   项目 / 构建 / 部署 / 主机 / 监控 / 用户  │
├─────────────────────────────────────────────┤
│  领域服务  BuildService / DeployService /      │
│           RollbackService / LogStreamService │
├─────────────────────────────────────────────┤
│  基础设施  GitClient(JGit) / DockerClient      │
│           (docker-java) / SshExecutor /       │
│           RegistryClient / 加密存储            │
├─────────────────────────────────────────────┤
│  存储     SQLite（元数据）/ Registry（镜像）     │
└─────────────────────────────────────────────┘
```

### 1.3 关键架构决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 目标主机管理 | **无 Agent**（SSH + docker CLI） | 主机端零安装，降低接入门槛；Opah 通过 SSH 执行 `docker pull / run / logs` 等命令并解析结果 |
| 构建 | Opah 容器挂载 `/var/run/docker.sock`，用 docker-java 调宿主机 daemon | PRD 已定（8.1 方式 A） |
| 镜像分发 | 内置 `registry:2` 容器，构建后 push，目标主机 pull | PRD 已定（8.2 方案②） |
| 元数据存储 | **内嵌 SQLite**（单文件，随 volume 持久化） | 支撑"单容器即用"的开箱体验；通过 JPA 屏蔽方言，未来可平滑切换 PostgreSQL |
| 代码拉取 | JGit（纯 Java 实现） | 无需在容器内安装 git CLI，clone/fetch/checkout 全部程序化操作 |
| 实时推送 | WebSocket（构建日志、容器日志、状态变更） | 双向通信，日志流场景成熟 |

## 3. 核心流程设计

### 3.1 构建流程（BUILD-02/03/04）

```
用户点击构建
    │
    ▼
① 创建 build 记录（状态 PENDING，入队）          ──构建队列（并发上限可配，默认 2）
    │
    ▼ worker 取任务
② JGit fetch 指定 commit（仓库本地缓存于 /data/opah/repos/{projectId}）
    │
    ▼
③ 读取 Dockerfile；无则按语言生成（BUILD-01 模板）
    │
    ▼
④ docker build（docker.sock，streaming 输出逐行写 DB + 推送 WebSocket）
    │
    ▼
⑤ docker tag → opah-registry:5000/{projectId}:{versionTag}
   versionTag = {yyyyMMddHHmmss}-{commit短hash}
    │
    ▼
⑥ docker push 至内置 registry → 状态 SUCCESS / 失败则 FAILED（保留日志）
```

- 构建日志：逐行落库（`build_log` 表，支持断线后回放）+ WebSocket 实时推送；
- 同一项目同时只允许一个构建在跑（队列内去重）。

### 3.2 部署流程（DEPLOY-01/02/07）——单镜像项目

```
用户选择「版本 + 主机 + 运行配置」点击部署
    │
    ▼
① 创建 deployment 记录（状态 RUNNING）
    │
    ▼
② SSH 目标主机：docker pull opah-registry:5000/{projectId}:{tag}
    │  ── 目标主机需配置可访问内置 registry（compose 内网地址，见 §7.2）
    ▼
③ 生成运行配置（名称规范：opah-{projectId}-{service}，labels 标记归属）
    │
    ▼
④ 停旧：docker stop + docker rm 旧容器（按 label 检索）
   起新：docker run -d --restart={policy} -p {ports} -e {env} -v {volumes} ...
    │  ── 顺序：先 pull 成功才允许停旧；pull 失败则部署中止，旧实例不受影响
    ▼
⑤ 等待容器状态 = running，超时（默认 30s）则判定失败 → 自动回退重启旧容器
    │
    ▼
⑥ deployment 状态 SUCCESS；项目「当前版本」指向该版本
```

> **停机窗口说明**：单机同端口无法双实例并存，MVP 采用「pull → stop → start」最小窗口方案；蓝绿/滚动更新（DEPLOY-05）留到 v0.2 通过端口错开 + 反代切换实现。

### 3.3 部署流程——Compose 多容器项目（DEPLOY-07）

```
① 项目根目录检出 docker-compose.yml（Opah 不修改业务容器定义）
② Opah 将其中的 image 字段替换/注入为本次构建产出的 registry 地址 + tag
   （仅替换标记为构建产物的服务，数据库等基础服务保持原样）
③ 生成 opah.deploy.{versionTag}.yml，SFTP 上传至主机工作目录
    /opt/opah/projects/{projectId}/
④ SSH 执行：docker compose -f opah.deploy.{tag}.yml -p opah-{projectId} up -d
⑤ 旧版本 compose 文件保留在主机上，回滚即重新 up 旧文件
```

### 3.4 回滚（DEPLOY-04）

回滚 = 一次指向历史版本的部署：镜像仍在内置 registry 中 → `docker pull 旧 tag → 停旧 → 起新`。不重新构建，全程 < 10s。

### 3.5 日志与监控（OPS-02/03、HOST-02/03）

| 能力 | 实现方式 |
| --- | --- |
| 容器日志实时流 | SSH 长连接执行 `docker logs -f --tail=200 {id}`，逐行转发 WebSocket；断开即中断 SSH |
| 日志关键词过滤 | 前端本地过滤（MVP），服务端 grep 过滤（v0.2） |
| 容器/主机状态 | 定时任务每 15s 并发 SSH 各主机执行 `docker ps --format json` + `df/free` 解析入库；前端 5s 轮询或 WebSocket 推送 |
| 启停/重启 | SSH 执行 `docker start/stop/restart`，操作写审计日志 |

> SSH 连接管理：每主机维护连接池（复用已认证连接），空闲 5 分钟回收，避免高频轮询反复握手。

## 4. 数据模型

### 4.1 ER 概览

```
user ─┐
      ├─▶ project ──▶ credential（Git 凭据，加密）
      │      │
      │      ├──▶ build（构建记录）──▶ build_log
      │      │
      │      └──▶ deployment ──▶ host
      │
      └─▶ audit_log
```

### 4.2 主要表结构

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `project` | id, name, git_url, ref, default_branch, credential_id, build_config(JSON), compose_enabled | 构建配置含 Dockerfile 路径、构建参数、语言模板选择 |
| `credential` | id, name, type(USERNAME_TOKEN/SSH_KEY), secret_cipher, iv | AES-256-GCM 加密存储 |
| `host` | id, name, ip, ssh_port, username, auth_credential_id, status, last_seen_at, os_info, docker_version | |
| `build` | id, project_id, commit_sha, commit_msg, version_tag, status(PENDING/RUNNING/SUCCESS/FAILED), duration_ms, triggered_by, log_excerpt | 版本唯一索引 (project_id, version_tag) |
| `build_log` | id, build_id, line_no, content, is_stderr, created_at | 构建输出逐行持久化 |
| `deployment` | id, project_id, build_id, host_id, status(RUNNING/SUCCESS/FAILED/ROLLED_BACK), config_snapshot(JSON), started_by, started_at, finished_at | config_snapshot 冻结端口/环境变量/挂载，回滚时直接复用 |
| `runtime_container` | id, deployment_id, host_id, docker_container_id, name, status, image_tag, started_at | 定时同步覆盖更新 |
| `audit_log` | id, user_id, action, target_type, target_id, detail(JSON), ip, created_at | |
| `user` | id, username, password_hash(BCrypt), role | MVP 单管理员 |

> 镜像本体不落业务库，registry 即存储；`build.version_tag` 与 registry tag 一一对应，删除策略见 §8。

## 7. 关键技术点

### 7.1 docker.sock 安全边界

- Opah 容器仅挂载 `docker.sock`，以 root 运行是硬性前提（文档需明示风险）；
- Web 层所有触发 docker 操作的接口必须登录鉴权 + 审计；MVP 单管理员，v0.2 引入角色；
- 暴露端口仅 `8787`（Web/API），registry 不对外网暴露。

### 7.2 目标主机访问内置 Registry

- `docker-compose.yml` 中 registry 与 server 同网络；主机侧统一配置 **insecure-registries / 或自签名证书**指向 Opah 宿主机 IP:5000；
- 主机接入向导（HOST-01）中自动检测并提示配置 `daemon.json`，检测通过才允许部署。

### 7.3 构建队列与并发

- 虚拟线程 worker 池消费 `build` 表（`status=PENDING AND queued_at` 最小者优先）；
- 并发上限可配置（默认 2，避免宿主机资源耗尽）；
- Opah 重启后扫描 `RUNNING` 状态的孤儿构建/部署标记为 `FAILED(中断)`，不自动续跑，由用户重新触发。

### 7.4 容器归属标识

所有由 Opah 创建的容器统一打 label：`opah.managed=true`、`opah.projectId=`、`opah.version=`。以此检索旧实例，避免误操作用户手工创建的容器。

### 7.5 磁盘治理

- Registry 镜像保留策略：每项目默认保留最近 **10 个版本**，定时任务通过 Registry GC API 清理（可配置）；
- `/data/opah/repos` 的 Git 缓存：fetch 增量更新，单项目缓存超过 1GB 告警；
- 构建日志保留 90 天，定时归档删除。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| docker.sock 等同 root 权限 | Opah 被攻破即失守宿主机 | 登录鉴权 + 审计 + 不暴露公网建议；文档明示部署边界 |
| SQLite 并发写 | 多构建并发时锁竞争 | WAL 模式；元数据写入量小，构建日志走批量异步写 |
| SSH 轮询规模 | 主机多时轮询风暴 | 15s 间隔 + 连接池 + 并发上限；>50 台主机再考虑推送方案 |
| insecure-registry 明文传输 | 内网可接受，跨网段有窃听风险 | 文档推荐自签名证书方案，接入向导双选项 |
| Compose 项目差异大 | 任意 yml 结构难统一处理 | MVP 约定：仅支持「单构建产物服务 + 标准基础服务」结构，文档列出约定 |
