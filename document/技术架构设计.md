## 1. 架构总览

### 1.1 部署视角

Opah 以 **Windows 绿色自包含包**为主用形态（zip 解压 → 双击 opah.exe），构建使用本机 Docker daemon，镜像经 SSH 管道分发（`docker save | ssh docker load`），不依赖任何镜像仓库；目标主机零安装（仅 SSH + Docker，无 Agent）：

```
┌───────────────────────── Opah 宿主机（一期：Windows） ─────────────────────────┐
│  ┌──────────────────────────────────────────────┐                             │
│  │ opah-server（jpackage app-image 内含裁剪 JRE） │                             │
│  │ opah.exe 双击 → 启动 REST/WebSocket → 拉起浏览器 │                             │
│  │ ┌──────────────────────────────────────────┐ │                             │
│  │ │ opah-web（React SPA，内嵌 server 静态资源）│ │                             │
│  │ └──────────────────────────────────────────┘ │                             │
│  │ SQLite + Git 缓存 + 密钥（./data，随包便携）   │                             │
│  └──────────────────┬───────────────────────────┘                             │
│                     │ named pipe（//./pipe/docker_engine）                     │
│  ┌──────────────────▼───────────────────────────┐   形态 B（v0.2）：Linux     │
│  │ Docker Desktop daemon（构建）                 │   Compose + docker.sock    │
│  └──────────────────┬───────────────────────────┘                             │
└─────────────────────┼───────────────────────────────────────────────────────────┘
                      │ docker save │ SSH 管道 │ docker load（无 Agent）
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
   ┌─────────┐   ┌─────────┐   ┌─────────┐
   │ 主机 A   │   │ 主机 B   │   │ 主机 C   │  目标主机：仅需 SSH + Docker
   │ docker  │   │ docker  │   │ docker  │
   └─────────┘   └─────────┘   └─────────┘
```

### 1.2 逻辑分层

```
┌────────────────────────────────────────────────────┐
│  前端 opah-web（React SPA）                          │
├────────────────────────────────────────────────────┤
│  接入层   REST Controller / WebSocket 端点 / 静态资源 │
├────────────────────────────────────────────────────┤
│  应用层   仓库 / 部署单元 / 构建 / 部署 / 配置中心 /     │
│           主机 / 监控 / 用户                          │
├────────────────────────────────────────────────────┤
│  领域服务  UnitScanService / BuildService /          │
│           TemplateService / DeployService /         │
│           RollbackService / ConfigService /         │
│           LogStreamService                          │
├────────────────────────────────────────────────────┤
│  基础设施  JGit / docker-java / SshExecutor(MINA) /  │
│           构建模板引擎 / 加密存储                       │
├────────────────────────────────────────────────────┤
│  存储     SQLite（元数据）/ 本机 Docker 镜像 /          │
│           Git 缓存（./data/repos）                    │
└────────────────────────────────────────────────────┘
```

### 1.3 关键架构决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 目标主机管理 | **无 Agent**（SSH + docker CLI） | 主机端零安装；Opah 经 SSH 执行 `docker load/run/logs/compose` 并解析结果 |
| 构建 | docker-java 连接本机 daemon（Windows: named pipe / Linux: docker.sock，非 DinD） | 产品文档 Q1 已定；本机可控外网代理，基础镜像拉取不受限 |
| 镜像分发 | `docker save` 流式导出 + SSH 管道 `docker load` | 产品文档 Q2 已定；流式管道不落地完整 tar，目标主机零 registry 配置 |
| **仓库与部署单元建模** | `project`（仓库）1..n `service`（部署单元） | 产品文档 Q9/PROJ-06：前后端可同仓库但独立构建、部署、回滚 |
| **配置中心** | Opah 内置：环境变量 + 配置文件随部署注入；Nginx 配置构建时渲染 | 产品文档 Q8/CONF 模块；配置不再散落服务器 |
| 构建模板 | 内置 Java(Spring Boot) / React / Vue 三类 Dockerfile + Nginx 模板 | 产品文档 Q6/BUILD-01；模板引擎渲染，后续按类型扩展 |
| 交付 | **Windows 绿色自包含包**：jpackage app-image（内嵌 jlink 裁剪 JRE）打成 zip | 产品文档 Q7 已定；解压双击即用，一期不签名，v0.2 补安装向导 |
| server 运行形态 | Windows 裸跑（主用）/ Linux Compose（v0.2） | 与交付决策一致 |
| 元数据存储 | 内嵌 SQLite（单文件，随 `./data` 持久化，Flyway 管理 schema） | 开箱即用；JPA 屏蔽方言，未来可切 PostgreSQL |
| 代码拉取 | JGit（纯 Java） | 无需用户安装 git CLI |
| 实时推送 | WebSocket（构建日志、容器日志、状态变更） | 双向通信，日志流场景成熟 |

## 3. 核心流程设计

### 3.1 仓库接入与部署单元识别（PROJ-01/06）

```
用户填写 Git 地址 + 凭据
    │
    ▼
① JGit ls-remote 连通性校验 → clone --bare 缓存至 ./data/repos/{projectId}
    │
    ▼
② 单元扫描（UnitScanService）：遍历仓库工作区
    ├─ 含 pom.xml / build.gradle 的目录 → 候选 Java 单元
    ├─ 含 package.json 的目录 → 候选前端单元（dependencies 判定 React / Vue）
    ├─ 根目录含 docker-compose.yml → 提示可作 Compose 项目
    └─ 含 Dockerfile → 标记「自带 Dockerfile」单元
    │
    ▼
③ 接入向导展示候选列表，用户勾选/调整 → 落库为 service（部署单元）
   每个单元记录 sub_path（仓库内相对路径）+ type（JAVA / REACT / VUE / COMPOSE / CUSTOM）
```

> 约定：单元识别结果仅是初始建议，用户可在向导中增删（如忽略 docs、mock 等含 package.json 的目录）。仓库根即单元时 `sub_path = .`。

### 3.2 构建流程（BUILD-01/02/03/04）

```
用户对某部署单元点击构建
    │
    ▼
① 创建 build 记录（PENDING 入队）        ──构建队列（并发默认 2，可配；同单元同时仅一个构建）
    │
    ▼ worker 取任务
② JGit fetch 指定 ref → checkout 到 ./data/repos/{projectId}/work/{serviceId}
    │
    ▼
③ 读取单元目录内 Dockerfile；无则由模板引擎按 type 渲染生成（BUILD-01）
   前端单元：nginx.conf 同步由 CONF-02 配置渲染（history 路由 / API 反代 / gzip）
    │
    ▼
④ docker build（本机 daemon，streaming 输出逐行写库 + WebSocket 推送）
    │
    ▼
⑤ docker tag → opah/{projectId}-{serviceId}:{versionTag}
   versionTag = {yyyyMMddHHmmss}-{commit短hash}；同单元版本号唯一
    │
    ▼
⑥ SUCCESS / FAILED（日志保留）；镜像留本机，部署时才 save 分发
```

- 构建日志逐行落库（`build_log`），支持断线回放（`afterLine` 增量拉取）；
- **改 Nginx 配置（CONF-02）需要重新构建**才生效（T3 已定：配置渲染进镜像）。

### 3.3 配置中心（CONF-01/02）

```
配置管理（service 级，UI 分「环境变量」与「配置文件」两页签）
    │
    ├─ 环境变量 config_entry：key/value（敏感项加密存储）
    │    部署时 → docker run -e K=V ...（即时生效，无需重新构建）
    │
    └─ 配置文件 config_file：如 application-prod.yml、logback-spring.xml
         部署时 → SFTP 上传 /opt/opah/projects/{projectId}/{serviceId}/config/
                 → -v 挂载进容器约定路径（如 /opah/config）
                 → Java 单元追加启动参数 --spring.config.additional-location=/opah/config/
```

- 部署时 `config_snapshot`（JSON）冻结本次生效的配置全量，回滚时随版本一起还原；
- 敏感值（勾选「敏感」）AES-256-GCM 加密落库，UI 回显打码，审计不记录明文；
- Nginx 配置（CONF-02）独立表单：路由模式（hash/history）、API 反代地址（前缀 + 上游）、gzip 开关 → 存 `service.nginx_config`，构建时渲染；
- 配置版本化与回退（CONF-03）v0.2：配置变更快照表 + diff。

### 3.4 部署流程（DEPLOY-01/02/03）——单镜像单元

```
用户选择「单元版本 + 主机 + 运行配置」点击部署
    │
    ▼
① 创建 deployment 记录，冻结 config_snapshot（端口/环境变量/挂载/配置文件版本）
    │
    ▼
② 镜像分发：docker save {image} | ssh {host} docker load
    ── 主机已有同 tag 镜像（docker image inspect 探测）则跳过传输
    ▼
③ 配置文件 SFTP 上传至主机工作目录（见 3.3）
    │
    ▼
④ 停旧：docker stop/rm 旧容器（按 label opah.serviceId 检索）
   起新：docker run -d --restart={policy} -p {ports} -e {env}
         -v {configfiles} --name opah-{projectId}-{serviceId} ...
    ── 顺序：load/上传成功才允许停旧；分发失败则中止，旧实例不受影响
    ▼
⑤ 等待容器 running（超时默认 30s 判失败 → 自动回退重启旧容器）
    │
    ▼
⑥ SUCCESS；单元「当前版本」指向该版本
```

> 单机同端口无法双实例并存，MVP 采用「load → stop → start」最小停机窗口；蓝绿/滚动（DEPLOY-05）v0.2 经端口错开 + 反代切换实现。

### 3.5 部署流程——Compose 多容器项目（DEPLOY-07）

```
① 单元检出 docker-compose.yml（Opah 不修改业务容器定义）
② 将标记为构建产物的服务 image 字段替换为本次镜像 tag
   （数据库等基础服务保持原样；产物镜像已 save/load 预分发）
③ 渲染 opah.deploy.{versionTag}.yml + 配置文件 → SFTP 上传
   /opt/opah/projects/{projectId}/{serviceId}/
④ SSH：docker compose -f opah.deploy.{tag}.yml -p opah-{projectId}-{serviceId} up -d
⑤ 旧 compose 文件保留在主机，回滚 = 重新 up 旧文件
```

### 3.6 回滚（DEPLOY-04）

回滚 = 指向历史 deployment 的一次重放（复用其 config_snapshot），优先复用**目标主机本地已 load 的历史镜像**：`docker image inspect` 命中 → 停旧起新，零传输秒级。镜像已被清理则从构建机本地历史 tag 重新 save/load 后执行。**不重新构建**；配置随 snapshot 还原。

### 3.7 日志与监控（OPS-01/02/03、HOST-02/03/04）

| 能力 | 实现方式 |
| --- | --- |
| 容器日志实时流 | SSH 长连接 `docker logs -f --tail=200 {id}`，逐行转发 WebSocket；断开即断 SSH |
| 关键词过滤 | 前端本地过滤（MVP），服务端过滤（v0.2） |
| 容器/主机状态 | 定时任务 15s 并发 SSH 各主机：`docker ps --format json` + `df -h` / `free -m` 解析入库；前端轮询/WS 推送 |
| 启停/重启 | SSH `docker start/stop/restart`，写审计日志 |
| 主机健康（HOST-05，P1） | 同上探活结果驱动状态与告警（v0.2） |

> SSH 连接池：每主机复用已认证连接，空闲 5 分钟回收，避免高频轮询反复握手。

## 4. 数据模型

### 4.1 ER 概览

```
user ─┐
      ├─▶ project（Git 仓库）──▶ credential（Git 凭据，加密）
      │       │
      │       └─▶ service（部署单元，PROJ-06）
      │             ├─▶ config_entry / config_file（配置中心）
      │             ├─▶ build ──▶ build_log
      │             └─▶ deployment ──▶ host ──▶ runtime_container
      │
      └─▶ audit_log
```

### 4.2 主要表结构

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `project` | id, name, git_url, default_branch, credential_id | 仓库级信息；不再直接挂构建 |
| `service` | id, project_id, name, type(JAVA/REACT/VUE/COMPOSE/CUSTOM), sub_path, build_config(JSON), nginx_config(JSON) | **部署单元**：独立构建/部署/回滚的最小单位；版本号在其内唯一 |
| `credential` | id, name, type(USERNAME_TOKEN/SSH_KEY), secret_cipher, iv | AES-256-GCM |
| `host` | id, name, ip, ssh_port, username, auth_credential_id, status, last_seen_at, os_info, docker_version | |
| `config_entry` | id, service_id, key, value_cipher, is_sensitive, updated_at | 环境变量；敏感项加密 |
| `config_file` | id, service_id, path, content, updated_at | 配置文件原文（含敏感内容的文件整体加密） |
| `build` | id, **service_id**, commit_sha, commit_msg, version_tag, status(PENDING/RUNNING/SUCCESS/FAILED), duration_ms, triggered_by, log_excerpt | 唯一索引 (service_id, version_tag) |
| `build_log` | id, build_id, line_no, content, is_stderr, created_at | 逐行持久化 |
| `deployment` | id, **service_id**, build_id, host_id, status(RUNNING/SUCCESS/FAILED/ROLLED_BACK), config_snapshot(JSON), started_by, started_at, finished_at | snapshot 冻结端口/环境变量/挂载/配置文件内容，回滚直接复用 |
| `runtime_container` | id, deployment_id, host_id, docker_container_id, name, status, image_tag, started_at | 定时同步覆盖更新 |
| `audit_log` | id, user_id, action, target_type, target_id, detail(JSON), ip, created_at | |
| `user` | id, username, password_hash(BCrypt), role | MVP 单管理员 |

> 镜像本体不落业务库：本机与目标主机的 Docker 镜像即存储，`build.version_tag` 与镜像 tag 一一对应，保留策略见 §7.6。

### 5.2 WebSocket（STOMP，`/ws`）

| Topic | 推送内容 |

## 7. 关键技术点

### 7.1 绿色包启动器（INST-02/03）

- jpackage app-image 的 launcher 即 opah.exe；JVM 参数经 jpackage 配置固化（`-XX:MaxRAMPercentage`、文件编码、时区）；
- 启动序列：绑定端口（8787 起探测）→ 初始化 ./data（密钥生成、Flyway 迁移）→ `Runtime.exec` 打开默认浏览器 → 控制台持续输出日志；
- Docker 检测：docker-java ping named pipe `//./pipe/docker_engine`，失败原因分类（未安装 / 未启动 / daemon 异常）驱动前端引导页；检测每 30s 重试，恢复后自动消除告警；
- 单实例锁：`./data/opah.lock`（文件锁），防止重复双击拉起两份。

### 7.2 本机 Docker 安全边界

- Windows 裸跑形态经 named pipe 直连 Docker Desktop，权限边界等同本机用户；Linux Compose 形态挂载 docker.sock（root 权限，文档明示风险）；
- 所有触发 docker 操作的接口必须登录鉴权 + 审计；
- 对外仅暴露 `127.0.0.1:8787`（默认绑定本机回环，局域网访问作为显式选项开放）。

### 7.3 镜像分发与目标主机前置条件

- 目标主机仅需 SSH + Docker，无任何 registry 配置；
- `docker save | ssh docker load` 流式管道，两端均不落地完整 tar；超大镜像（GB 级）保留未来接入外部 registry 的扩展位；
- 目标主机镜像按版本保留（回滚依赖，见 §7.6）。

### 7.4 构建模板引擎

- 模板资源置于 server jar 内 `classpath:templates/`：`java-springboot.df`、`node-nginx.df`、`nginx.conf.hbs`（React/Vue 共用 node-nginx，差异为构建命令与 dist 目录参数）；
- 参数来源：`service.build_config`（JDK/Node 版本、构建命令覆盖）+ `service.nginx_config`（CONF-02）；
- 生成物写入工作目录后交 docker build；模板版本随 Opah 升级，已生成 Dockerfile 的单元记录所用模板版本便于追溯；
- 用户自带 Dockerfile 的 CUSTOM 单元不做任何改写。

### 7.5 构建队列与并发

- 虚拟线程 worker 池消费 `build` 表（PENDING 按 queued_at 最小优先）；
- 并发上限默认 2（防宿主机资源耗尽）；同单元同时仅一个构建，重复触发直接返回进行中的 build；
- Opah 重启后扫描孤儿 RUNNING 构建/部署 → 标记 FAILED(interrupted)，不自动续跑。

### 7.6 磁盘治理

- 构建机本地镜像：每单元保留最近 10 个 tag，定时 `docker rmi` 清理（可配）；
- `./data/repos` Git 缓存：fetch 增量；工作区按单元隔离（`work/{serviceId}`），构建后可清理工作区仅留 bare 缓存；
- 构建日志保留 90 天；配置文件随 deployment snapshot 永久可追溯；
- 目标主机：每单元保留最近 10 个版本镜像，未被 deployment 引用的定时清理。

### 7.7 容器归属标识

Opah 创建的容器/compose 项目统一打 label：`opah.managed=true`、`opah.projectId=`、`opah.serviceId=`、`opah.version=`；以此检索旧实例，不误伤用户手工容器。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| docker 控制权等同宿主机权限 | Opah 被攻破即失守宿主机 | 默认绑定 127.0.0.1 + 登录鉴权 + 审计；文档明示边界 |
| SQLite 并发写 | 多构建并发锁竞争 | WAL 模式；日志批量异步写 |
| SSH 轮询规模 | 主机多时轮询风暴 | 15s 间隔 + 连接池 + 并发上限；>50 台再考虑推送方案 |
| save/load 大镜像 | 耗时/占带宽 | 流式管道；保留策略控规模；保留外部 registry 扩展位 |
| 单元自动识别不准 | monorepo 结构千差万别 | 识别仅作建议，向导中人工确认；sub_path 可手改 |
| 模板覆盖度不足 | 非标项目构建失败 | CUSTOM 类型直用项目 Dockerfile 兜底；模板参数持续补充 |
| 敏感配置泄露 | 配置中心集中存密 | AES-256-GCM + 密钥文件权限控制；UI 打码；审计不落明文 |
| 无签名绿色包 | SmartScreen 告警 / 杀软误报 | README 说明；版本稳定后上 OV 证书（v0.2） |
| Compose 项目差异大 | 任意 yml 难统一处理 | MVP 约定「构建产物服务 + 标准基础服务」结构，文档列明约定 |
